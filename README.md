# BMBA Mock Test Pipeline

Автоматизированный конвейер для создания Mock-тестов по математике в формате
Национального сертификата BMBA.

Архитектура: оцифровка прошлых PDF-вариантов → генерация новых задач по
образцу (двухэтапный промпт с защитой от подмены чисел) → JSON, готовый для
передачи в вёрстку (matplotlib + WeasyPrint, отдельный проект).

## Установка

```bash
pip install -r requirements.txt
export GEMINI_API_KEY="ваш_ключ"
```

## Использование

### 0. Куда класть PDF-моки

Никакого фиксированного места не требуется — путь передаётся аргументом.
Удобнее всего создать одну папку рядом с проектом и сложить туда все сканы:

```
bmba_pipeline/          ← этот проект
moks/                   ← ваша папка, создайте сами
  PROMOCK-1.pdf
  PROMOCK-2.pdf
  PROMOCK-3.pdf
  ...
data/                   ← создаётся автоматически (SQLite база)
output/                 ← создаётся автоматически (экспортированные JSON)
```

Имя файла станет именем варианта (`variant_name`) в базе — например,
`PROMOCK-2.pdf` → вариант `PROMOCK-2`. Так удобно потом смотреть, откуда
пришла каждая задача.

### 1. Оцифровка одного PDF

```bash
python -m bmba_pipeline.cli digitize moks/PROMOCK-1.pdf --variant PROMOCK-1 --export
```

Задачи сохраняются в SQLite (`data/problems.db`) и, с флагом `--export`,
дополнительно в `output/PROMOCK-1.json`.

### 1b. Оцифровка всех PDF из папки за один запуск

Если моков много — не нужно вызывать команду для каждого вручную:

```bash
python -m bmba_pipeline.cli digitize-batch moks/ --export --skip-existing
```

- Проходит по всем `*.pdf` в указанной папке.
- `--skip-existing` — пропускает файлы, чьё имя уже есть как вариант в базе
  (удобно при повторном запуске после того, как часть файлов уже обработана).
- Если один файл падает с ошибкой (например, модель вернула невалидный
  JSON) — batch не останавливается, а продолжает со следующим файлом и
  выводит список проблемных в конце, чтобы перезапустить только их.

### 2. Проверка накопленной базы

```bash
python -m bmba_pipeline.cli stats
```

Покажет количество задач-доноров, распределение по темам и сложности —
именно эта структура будет воспроизведена в новом тесте.

### 3. Генерация нового мок-теста

```bash
python -m bmba_pipeline.cli generate --variant mock-2026-09
```

Результат: `output/mock-2026-09.json` + сводка `test_summary` в консоли для
сверки со структурой базы.

## Запуск на GitHub Actions

Идея: репозиторий хранит и код, и данные (`data/problems.db`, `moks/`,
`output/`). Каждый workflow при запуске скачивает актуальную копию
репозитория (со всей накопленной базой), делает свою работу и **коммитит
изменения обратно** — иначе виртуалка Actions забудет всё после завершения
job'а, так как это одноразовое чистое окружение.

### Шаг 1 — создать репозиторий и залить проект

```bash
cd bmba_pipeline
git init
git add .
git commit -m "init"
git branch -M main
git remote add origin git@github.com:ваш-логин/bmba-pipeline.git
git push -u origin main
```

Положите PDF-моки в `moks/` и закоммитьте их тоже (или добавляйте по мере
появления новых вариантов).

### Шаг 2 — добавить секрет с API-ключом

GitHub → ваш репозиторий → **Settings → Secrets and variables → Actions →
New repository secret**:
- Name: `GEMINI_API_KEY`
- Value: ваш ключ Gemini

Workflow берёт его как `${{ secrets.GEMINI_API_KEY }}` — ключ никогда не
попадает в код или логи.

### Шаг 3 — два готовых workflow (уже лежат в `.github/workflows/`)

**`digitize.yml`** — оцифровка. Запуск только вручную:
GitHub → вкладка **Actions** → "Digitize BMBA mocks" → **Run workflow**.
Проходит по всем PDF в `moks/`, пропуская уже оцифрованные (`--skip-existing`),
и коммитит обновлённую `data/problems.db`.

**`generate.yml`** — генерация нового мок-теста. Два способа запуска:
- **По расписанию** — по умолчанию каждый понедельник в 06:00 UTC
  (строка `cron: "0 6 * * 1"` — поменяйте под свой график, например
  `"0 6 * * *"` для ежедневного запуска).
- **Вручную** — вкладка Actions → "Generate new BMBA mock" → Run workflow,
  можно указать имя варианта (иначе возьмётся текущая дата).

Результат сохраняется двумя способами:
1. Коммитится в `output/<variant>.json` — виден прямо в репозитории.
2. Дополнительно выкладывается как **Actions Artifact** — можно скачать
   зип с вкладки конкретного запуска, не копаясь в истории коммитов.

### Важно про параллельность

Оба workflow пишут в один и тот же SQLite-файл и коммитят в один и тот же
репозиторий — если запустить их одновременно, возможен конфликт при пуше.
В файлах уже стоит `concurrency: group: bmba-pipeline-write`, которая не
даёт двум запускам работать параллельно (второй встанет в очередь).

### Если база разрастётся

SQLite-файл в git — нормальное решение, пока база в пределах десятков МБ.
Если задач станет очень много и коммиты станут тяжёлыми, вариант на будущее —
перейти на `actions/cache` для базы вместо коммита в git, либо вынести
хранилище во внешнюю БД (Postgres/Supabase) — но для текущего масштаба
проекта это избыточно.

## Структура проекта

```
.github/workflows/
  digitize.yml  — Actions: оцифровка всех PDF из moks/ (запуск вручную)
  generate.yml  — Actions: генерация нового мока (по расписанию/вручную)
bmba_pipeline/
  config.py     — настройки, модели, пути
  db.py         — SQLite-хранилище задач
  prompts.py    — промпты Режима 1 и Режима 2 (v2, с anti-copy чеклистом)
  digitize.py   — Режим 1: PDF → JSON через Gemini
  generate.py   — Режим 2: база → новый тест через Gemini
  validate.py   — устойчивый парсинг JSON + проверка схемы
  cli.py        — команды digitize / digitize-batch / stats / generate
moks/           — сюда кладёте PDF-сканы (создайте сами, коммитите в git)
data/           — SQLite база (создаётся автоматически, коммитится в git)
output/         — экспортированные JSON (создаётся автоматически)
```

## Важно

- Модель Gemini для генерации указана в `config.py` (`GENERATE_MODEL`) —
  проверяйте актуальное название модели в документации Gemini API, так как
  версии периодически обновляются.
- `validate.py` ловит структурные ошибки (отсутствие полей, некорректная
  сложность, разрывы в нумерации), но НЕ проверяет математическую
  корректность решений — это остаётся на ручную/выборочную проверку.
- Промпт Режима 2 (`prompts.py`) заставляет модель проходить два этапа
  (абстракция скелета задачи → инстанциация с изменением контекста/вопроса/
  конфигурации), чтобы избежать эффекта "просто заменили числа".
